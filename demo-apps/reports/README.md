# Reports demo (Lumen Reports)

Private `@pepbits-demo/reports`, using Next.js 16.3.3, React 19.2 and Tailwind 4.1. Phase 6e-1 ports the **Lumen Reports reference module** (`desktop-clients/packages/reference-reports`, read-only) into its own app: all **19 source page routes** plus the signed-download host adaptation. Every report, user, schedule, email and number is **fictional demonstration data** generated by the unchanged demo API. No email is sent and nothing here is a production reporting service. This is a local build/run, not a deployment.

## Run locally

From the repository root:

```sh
npm install
# Start the unchanged API using its documented Node 24/runtime environment.
node mock-api/server.mjs
NEXT_PUBLIC_API_URL=http://localhost:3330 npm run dev -w @pepbits-demo/reports
```

Use the actual API port/origin from the [API guide](../../mock-api/README.md). Dev/start use port **3350**. Sign in with a local fixture account from the API fixtures (credentials are not repeated here); the administrator, finance-manager and operations-analyst fixtures can open Reports. The optional same-origin proxy accepts these settings in an ignored app `.env.local`:

```dotenv
NEXT_PUBLIC_API_URL=/api
REPORTS_API_URL=http://127.0.0.1:3330
```

The public URL is build-time configuration; `REPORTS_API_URL` is server-only and the proxy forwards file `Content-Disposition` headers for downloads. Components never hold an origin: they receive the authenticated request callback. Scripts are `dev`, `build`, `start`, `typecheck`, `test` and `test:integration`:

```sh
NEXT_PUBLIC_API_URL=/api npm run build -w @pepbits-demo/reports
npm run typecheck -w @pepbits-demo/reports
npm test -w @pepbits-demo/reports
npm run test:integration -w @pepbits-demo/reports
```

Build before integration. The shared launcher (`tooling/scripts/run-demo-integration.mjs reports`) starts one API, one production Next server and Chromium on free loopback ports with temporary API storage, and stops all three on success, failure, cancellation or deadline. Set `REPORTS_API_NODE` to a Node 24 executable. If generated API runtimes are absent, `REPORTS_RUNTIME_ARTIFACTS` can name a source-identical API checkout; every tracked API file is hash-compared before reuse. Chromium on this machine needs `LD_LIBRARY_PATH=$HOME/.local/opt/pw-libs/root/usr/lib/x86_64-linux-gnu`. Optional receipts: `REPORTS_RESULT`, `REPORTS_IDENTITY`, `REPORTS_SCREENSHOT`; cancellation/deadline: `REPORTS_STOP_FILE`, `REPORTS_TIMEOUT_MS`; build output: `REPORTS_BUILD_DIR`. Keep at most one Next server, one API and one Vitest tree running. The [delivery record](../../docs/releases/unreleased/restructure-phase-6e-1-2026-10-24.md) identifies exact checks and limits.

## Structure and routes

| Path | Responsibility |
| --- | --- |
| `src/app` | Next root layout (persistent client host), catch-all page and the optional same-origin API proxy |
| `src/providers.tsx` | Public `ApplicationProviders`: session → API preferences/tenant policy → runtime catalog → shell |
| `src/navigation.ts` | The `reference-reports` shell module, source sidebar sections, page definitions, role visibility and deep-link mapping |
| `src/renderer.tsx` | Public page-engines renderer registry (`reports`, `preferences`) |
| `src/adapters` | Configured HTTP (`@pepbits/platform/http`) and the reports transport (namespace, routing headers, error mapping) |
| `src/modules/reports` | Lumen Reports configuration and screens: routes, client, pages, viewer, builder, dashboards, jobs, schedules, email requests, API keys, administration |

URLs are the source paths: `/`, `/reports`, `/reports/:id`, `/builder`, `/builder/:id` (`new`), `/dashboards`, `/dashboards/:id`, `/jobs`, `/jobs/:id`, `/schedules`, `/email-in`, `/api-keys`, `/admin/{access,users,settings,sources,audit,outbox}` and `/login`. `/downloads/:token` opens signed outbox links; `/preferences` is the shared settings page. Queries such as `/admin/audit?q=…&action=…` and `/reports?denied=1` are part of the deep link and survive refresh. Unknown paths show not-found. AI is off.

## Host, data and preferences

The app uses the shared host exactly like healthcare and ERP: sign-in, session lock, preferences with one serialized update path, tenant locks/allowed values, runtime localization from `/localization`, theme, fonts and the full shell chrome. The module host (`src/modules/reports/host.tsx`) only carries the authenticated scope, effective preferences, the configured transport and module-relative navigation; everything below it is keyed by tenant/application/branch/user/roles, so an identity change drops module state and in-flight responses.

The transport maps the source `/api/...` paths to `/reference-modules/reports/api/...` with `X-Product-Id: nexora`, `X-Reference-Module: reference-reports` and the session branch. These are routing metadata only: the demo API derives the actor from the bearer session and enforces every permission, report grant, branch row scope and masking rule. Server denials (`PAGE_DENIED`, `REPORT_DENIED`, `BUILDER_REDIRECT`) become host navigation to `/?denied=1`, `/reports?denied=1` and `/builder`. Shell visibility mirrors the API navigation configuration (administration pages for administrators) and is not authorization.

Effective preferences apply throughout: `pageSize` (with locks and allowed values) drives the viewer and stored-result pages and resets paging; density, stripes, sticky headers and wrapping reach every shared table; dates, times, numbers, currency and percentages use the preference formatter (instants shown in the organisation reporting time zone); `exportFormat` orders and, when managed, narrows export formats; the module search shortcut (Ctrl/⌘+Shift+K) binds only while keyboard shortcuts are on; reduced motion stops module transitions; loading uses skeletons when enabled. Notifications go through the shared shell toast viewport, so toast position, duration, style and count follow the shell preferences.

Library reuse: shared Button/Input/Select/Textarea/Toggle/Checkbox/MultiSelect/Date/Time controls, Card, Modal, ConfirmDialog, ActionMenu, Table/Pagination, empty/error/loading states, `BarChart`/`LineChart`/`DonutChart`, `PrintDocument`, ScreenHost notifications and the page-engines renderer. Layout classes in `reports.css` are scoped under `.lumen-reports` and use semantic tokens, `--radius` and the font scales.

## Completion boundary

All 19 source pages and their workflows are ported: overview, library (search, categories, favourites), viewer (date range presets/custom dates, extra filters, range meter, saved personal/role views, favourites, column picker, charts, paged and sorted table with totals and masked columns, CSV/XLSX/JSON export, print, email, background runs, schedules), builder with preview, save and delete, dashboards (create, edit widgets, shared period, share, delete), background jobs with stored result pages, cancellation and downloads, schedules (create, pause/resume, run now, process due, delete), email-in simulation, API keys with BI pull instructions, and administration (roles and access matrix, users, settings and rules, data sources, audit filter, email outbox with signed links).

Differences from the source module, all host integration: the module toast region is replaced by the shell toast viewport; charts use the library chart components (keyboard inspection through a native select instead of per-mark hover only); Print renders an isolated copy (title, period and the current result page with totals) through the shared `PrintDocument` instead of printing the whole window; the module `main` landmark became a region inside the shell's `main`; dashboard widget titles became level-2 headings. Remaining limits: no original-source pixel comparison; the fictional store keeps state in memory only (restart loses it), advances jobs per request and never sends email; the BI `/api/v1` endpoints are exercised by direct HTTP, not a BI tool; human language, accessibility and domain review remain pending. See the [source mapping](source-mapping.md) and [feature contract](../../docs/features/reports-demo.md).
