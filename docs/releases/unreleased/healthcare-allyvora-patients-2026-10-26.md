## Changes and compatibility

AllyVora Patients is the fourteenth healthcare header app, with three entries and `/allyvora-patients/patients` URL modes for list/new/view/edit plus `/allyvora-patients/settings/layout`. The 99-field definition, five layouts, wristband, rules drawer, activity, status and admin layout setup match standalone. One healthcare application host supplies session, preferences, localization and shell; only business-module state is added. The [feature contract](../../features/healthcare-demo.md#allyvora-patients--hcd-av), [app guide](../../../demo-apps/healthcare/README.md#allyvora-patients--fourteenth-app) and [source mapping](../../../demo-apps/healthcare/source-mapping.md) document use, permissions, failures, adaptation and provenance.

The boundary gate prohibits private-demo dependencies, so the owner-authorized copy fallback preserves standalone UI. Both use the same unchanged file-linked `@allyvora/shared` form package. Existing healthcare routes are unchanged. New-registration drafts are memory only and clear on module exit/identity change. Effective preferences/tenant locks remain authoritative. UI grants match standalone; the unchanged AllyVora API simulates its own user without role enforcement. English form wording, pointer signature, global command-source and durable-draft limitations remain as in standalone; this is fictional software demonstration, not clinical acceptance.

Root tooling builds the unchanged backend in a disposable copy, installs locked production dependencies and the Node 24 linux-x64 glibc prebuilt SQLite binary, and packages it under `src/allyvora-backend`. It never builds inside protected `source/`. Archive inventory hashes include backend provenance. Package and verify smoke actual create/edit/status/audit/layout requests through both packaged web proxies. No outer manifest fields or receiver schema version change.
