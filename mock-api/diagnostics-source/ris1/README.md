# Radiant RIS

A radiology information system and PACS built with Next.js 14. It covers the department's whole workflow: ordering, scheduling, arrival, billing, the technologist's exam, image archiving, reporting and sign-off, critical results, turnaround time tracking, and HL7, FHIR and DICOM integration with other systems.

> The demo images are synthetic phantoms generated by the app. Nothing here is validated for clinical or diagnostic use.

## Quick start

You need Node.js 18.18 or later. `better-sqlite3` compiles a native module on install, so on Windows you may need the Visual Studio C++ build tools; on Linux and macOS it normally downloads a prebuilt binary.

```bash
npm install
npm run dev          # http://localhost:3000
```

The first request creates the SQLite database in `./data` and loads demo data: 24 patients, about 70 orders in every workflow state, 14 studies with synthetic images, reports, a critical result and an addendum. To start again from clean demo data:

```bash
npm run seed
```

For production use `npm run build && npm start`.

There is no login screen. Use the name in the top right corner to switch between demo staff; every action and signature is recorded against the selected person.

## Walking through the workflow

1. **Order.** On *Orders → New order*, find or register the patient, tick one or more procedures (each gets its own accession number), set the priority, referrer, clinical history and, optionally, an appointment. An invoice is raised from the procedure price. Orders also arrive from the HIS over HL7 or FHIR.
2. **Schedule and arrive.** *Schedule* shows the day by modality and the orders still waiting for a slot. *Arrivals* checks patients in, shows allergies and preparation, and flags unpaid balances.
3. **Exam.** The *Technologist worklist* starts the exam. *Acquire images* plays the part of the scanner: it generates a synthetic study for that accession and sends it to the archive. *Complete* records contrast, dose and notes; completing without images needs explicit confirmation.
4. **Read.** The *Reading worklist* is sorted by priority and by time against the turnaround target. The reporting workstation puts the image viewer beside the report:
   - templates and normal reports, with `___` blanks you jump between with **F2**;
   - one-click macros;
   - structured scoring for TI-RADS, BI-RADS, Lung-RADS, PI-RADS and LI-RADS, which writes the category and recommendation into the report;
   - speech-to-text dictation (**F4**), with spoken punctuation ("period", "comma", "new paragraph") and "next field";
   - measurements from the viewer (length in mm, ROI mean and SD in HU) that you click to insert;
   - prior exams with their images and impressions;
   - autosave every 20 seconds and **Ctrl+S**;
   - preliminary sign-off (residents), final sign-off (radiologists), addenda, and amendments that require a reason and keep every version.
5. **Critical results.** Ticking *Critical finding* before signing opens a critical result with an urgency (red 1 hour, orange 6 hours, yellow 3 days). *Critical results* records who was told, how, and whether they read it back, then closes it. The communication is printed on the report.
6. **Bill and print.** Take payments from the order, *Arrivals* or *Billing*; print receipts and reports from the order page.

**Dictation** uses the browser's built-in speech recognition, so it works in Chrome, Edge and Safari but not Firefox. Chrome sends the audio to Google's speech service; check that this is acceptable before dictating anything real.

## Image viewer

The viewer reads DICOM Part 10 files in the browser (`dicom-parser`) and supports:

- window and level by dragging, with CT presets (soft tissue, lung, bone, brain, stroke, abdomen, liver);
- zoom, pan, invert, and stack scrolling with the mouse wheel or arrow keys;
- cine for stacks and multi-frame images;
- length and ROI measurement;
- series thumbnails and a DICOM header panel.

It handles uncompressed transfer syntaxes. Compressed images are stored but not displayed. Open any study full screen at `/viewer/<studyId>`.

## Integration

Three small helper services run beside the web app. Start each in its own terminal while `npm run dev` is running:

```bash
npm run mllp          # HL7 MLLP listener on :2575, plus a mock EMR on :2576 that ACKs results
npm run dicom:scp     # DICOM Storage SCP, AE RADIANT_RIS on :11112
npm run dicom:samples # write test DICOM files for each modality to ./samples
```

The *Integration* page shows every message in and out, lets you resend failed ones, tests each interface, and has a simulator that sends sample HL7 and FHIR messages to the RIS.

### Inbound

| What | Endpoint | Notes |
|---|---|---|
| HL7 v2 over MLLP | `tcp://host:2575` | `ORM^O01` with control codes NW (new), CA (cancel), XO (change) and SC (status); `ORU^R01` (outside results); `ADT^A04/A08/A31`. Replies AA (accepted), AE (validation error) or AR (processing error). |
| HL7 v2 over HTTP | `POST /api/integration/hl7` | The body is the raw message; the response body is the ACK. |
| FHIR R4 | `POST /api/fhir/ServiceRequest` | Returns the ServiceRequest with the accession number, or an OperationOutcome. |
| DICOM C-STORE | AE `RADIANT_RIS`, port 11112 | Images are matched to orders on Accession Number (0008,0050). |
| DICOMweb STOW-RS | `POST /api/dicomweb/studies` | `multipart/related; type="application/dicom"` |
| Upload | PACS page | Drag and drop `.dcm` files. |

Inbound orders are validated before anything is created:

- the procedure code must be in the test master;
- the patient ID and name are required;
- duplicate placer order numbers and duplicate message control IDs are rejected;
- unknown patients and referrers are registered automatically.

Images whose accession does not match an order wait in PACS as *Unmatched* until someone links them.

### Outbound

These are configured under *Masters → Interfaces*. Each interface subscribes to the events it should receive:

| Event | Sent when | HL7 | FHIR |
|---|---|---|---|
| ORDER_NEW, ORDER_UPDATE, ORDER_CANCEL | An order is created, changed or cancelled (including RIS-placed orders forwarded to other systems) | ORM^O01 (NW / XO / CA) | ServiceRequest |
| REPORT_PRELIM, REPORT_FINAL, REPORT_CORRECTED | A report is signed, receives an addendum or is amended | ORU^R01 (P / F / C) with the report text in OBX segments and the Study Instance UID | DiagnosticReport |
| STUDY_ROUTE | An exam is completed, or a study is sent from PACS | DICOM C-ECHO, then C-STORE of every image | |

Outbound transports are HL7 over MLLP (ACKs are checked), HL7 over HTTP, FHIR REST and DICOM C-STORE.

Other read endpoints:

- `GET /api/mwl?ae=CT_SOMATOM` gives the modality worklist as JSON.
- `GET /api/dicomweb/studies` is a QIDO-RS study search.
- `GET /api/fhir/DiagnosticReport?identifier=<accession>` returns the signed report.

### Examples

```bash
# New order over HTTP
printf 'MSH|^~\\&|EPIC|CITYGEN|RADIANT|RADIOLOGY|20260101120000||ORM^O01|MSG0001|P|2.5.1\rPID|1||H123456^^^CITYGEN^MR||OKAFOR^AMARA||19780412|F\rPV1|1|E\rORC|NW|HIS1234567\rOBR|1|HIS1234567||CT-CTPA^CT Pulmonary angiography|S||||||||Pleuritic chest pain\r' \
  | curl -s -X POST --data-binary @- http://localhost:3000/api/integration/hl7

# FHIR order
curl -s -X POST http://localhost:3000/api/fhir/ServiceRequest -H 'Content-Type: application/fhir+json' -d '{
  "resourceType":"ServiceRequest","status":"active","intent":"order","priority":"urgent",
  "identifier":[{"value":"EMR-1001"}],"code":{"coding":[{"code":"MR-BRAIN"}]},
  "contained":[{"resourceType":"Patient","id":"p1","identifier":[{"value":"E5501"}],"name":[{"family":"Silva","given":["Marta"]}],"gender":"female","birthDate":"1990-06-21"}],
  "subject":{"reference":"#p1"}}'

# Send sample images over DICOM (DCMTK), or with an accession that matches an order
npm run dicom:samples -- --modality CT --accession R2610010001
storescu -aec RADIANT_RIS localhost 11112 samples/CT_chest/*.dcm
```

The *Long-term archive PACS* interface points at the bundled SCP (127.0.0.1:11112) and is inactive by default. Activate it to see completed exams routed automatically. The *Teleradiology* and *Regional FHIR repository* interfaces post to a built-in echo endpoint so that outbound traffic succeeds without external systems.

## Masters

*Masters* (administrator only) maintains:

- **Modalities:** AE title, room and daily capacity.
- **Procedures:** code, CPT, price, slot length, contrast and preparation.
- **Report templates:** normal reports, templates with blanks, and macros.
- **TAT targets:** by priority, with optional per-modality overrides; for example, routine MR 48 hours and STAT CT 45 minutes.
- **Referring doctors, staff and roles, and interfaces.**

Deactivating a record keeps historical orders intact.

Report turnaround runs from exam completion to final signature. An exam is *at risk* after 75% of its target, and *TAT & analytics* reports compliance by modality, priority and radiologist.

## Project layout

```
src/app/(ris)/        pages inside the application shell
src/app/viewer/       full-screen image viewer
src/app/print/        printable report and receipt
src/app/api/          REST, HL7, FHIR and DICOMweb endpoints
src/components/       UI kit, DICOM viewer, structured reporting, dictation
src/lib/              database, workflow rules, reports, HL7, outbound delivery, inbound processing
src/lib/dicom/        DICOM writer, synthetic study generator, ingest, DIMSE client
scripts/              seed, MLLP bridge, DICOM SCP, sample generator
```

Data lives in SQLite (`better-sqlite3`, raw SQL; the schema is in `src/lib/db.ts`). Images are stored as files under `storage/dicom/<study>/<series>/`. Settings are listed in `.env.example`.

## Before real use

This is a complete, working reference implementation, not a certified medical device. Before handling real patient data it would need:

- real authentication, such as SSO or OIDC, in place of the user switcher;
- encryption and backups for the database and the image archive;
- HTTPS and TLS for HL7 and DICOM traffic;
- a production database such as PostgreSQL if several app servers share it;
- validated viewing software for primary diagnosis;
- local regulatory review.
